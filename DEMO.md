# rustemd — interactive live environment

A minimal, **interactive** environment for driving a real rustemd PID-1 daemon
by hand: build a busybox initramfs, boot it in qemu, and drop into a getty
shell on `/dev/ttyS0` where you can type `rustemd …` commands against the live
manager. It ships one friendly demo unit of **every type rustemd supports**
(`.service`, `.socket`, `.timer`, `.mount`, `.target`) plus runtime-generated
`.device` units from udev enumeration.

```
scripts/live-vm.sh            # build the initramfs and boot it interactively
```

## Build & run

```bash
# 1. Build the PID-1 binary + TUI (boot feature = mount API filesystems,
#    instantiate getty; already includes socket + udev).
cargo build --release --features boot

# 2. Boot it. qemu -nographic with the serial console wired straight to your
#    terminal (stdin+stdout pass through — this is what makes it interactive).
scripts/live-vm.sh            # auto-discovers a kernel; pass one as $1 if not
```

Inside the VM you land on a busybox getty (`/dev/ttyS0`, shell is `/bin/sh`).
Try:

```sh
rustemd list-units                      # see .device units appear (udev)
rustemd status demo.service demo.mount demo.socket demo.timer demo.target
rustemd start demo.mount && ls /mnt/demo
rustemd is-active demo.mount
rustemd list-timers
printf 'hi\n' | nc 127.0.0.1 8080          # socket-activates demo-echo.service
rustemd status demo-echo.service
rustemd poweroff                        # clean shutdown
```

Quit at any time with `rustemd poweroff`, or force qemu to exit with `Ctrl-A x`
(`-nographic` multiplexes qemu's monitor onto the same keys).

## The demo units (`examples/live/`)

Each file is a self-contained, self-explanatory stub. `demo.target` is enabled
at boot (symlinked into `default.target.wants/`), so everything below starts
when the manager boots into `default.target`.

| Unit                  | Type       | What it demonstrates |
|-----------------------|------------|----------------------|
| `demo.service`        | `.service` | `Type=oneshot` greeting to `/dev/console`; `RemainAfterExit=yes` parks it in `active(exited)` so `status` is satisfying. |
| `demo.timer`          | `.timer`   | Monotonic schedule (`OnBootSec=10s`, `OnUnitInactiveSec=30s`) firing `demo-tick.service`. |
| `demo-tick.service`   | `.service` | The one-shot job the timer fires; logs a line per elapse. |
| `demo.socket`         | `.socket`  | `ListenStream=127.0.0.1:8080` (TCP); socket-activates `demo-echo.service` on the first connection (inetd-style). |
| `demo-echo.service`   | `.service` | The service socket-activation starts; announces itself, then idles. |
| `demo.mount`          | `.mount`   | Mounts a `tmpfs` at `/mnt/demo` on start, unmounts on stop (`active(mounted)`). |
| `demo.target`         | `.target`  | Groups the others (`Wants=`/`After=`); the unit the initramfs enables at boot. |
| (none)                | `.device`  | **No unit file.** Runtime-generated by udev enumeration (`/sys` + netlink); see below. |

### Why the timer uses `OnUnitInactiveSec` (and not only `OnUnitActiveSec`)

`OnUnitActiveSec` re-fires only while the target is **active**, and rustemd's
`start` on an already-active unit is a no-op — so pairing it with a
`RemainAfterExit=yes` service produces no visible re-run. The classic systemd
idiom for "run a one-shot job periodically" is `OnUnitInactiveSec` (target is
inactive between runs, so each elapse genuinely re-runs it), which is what
`demo.timer` demonstrates.

### `.device` units are runtime-generated

There is deliberately **no `.device` unit file** — systemd (and rustemd) derive
device units from the kernel, not from disk. The live env's `/init` mounts
`/proc`, `/sys` (sysfs) and `/dev` (devtmpfs) before exec'ing the daemon, so
the `udev` feature's sysfs walk registers a `.device` unit per device
(`sys-devices-…device` / `sys-<subsystem>-<name>.device`). `rustemd list-units`
shows them; `rustemd status sys-tty-ttyS0.device` works, for example.

## TUI over serial — honest status

`rustemd-tui` is ratatui/crossterm: it needs raw mode, an alternate screen and
cursor addressing. **Over the dumb serial console it does not render.**
Tested in the booted VM: `stty size` fails (the `ttyS0` line has no
`TIOCGWINSZ` size, so crossterm sees a 0×0 terminal), and running
`rustemd-tui` only emits cursor-hide/color-reset escape sequences with no
usable frame — no visible list. The process runs (and is killed cleanly by a
timeout) but draws nothing.

**The CLI is the primary interactive path in the VM.** To use the TUI, run it
against the daemon's control socket from a real terminal on the host (it needs
a real TTY with a window size):

```sh
# host, after starting the daemon somewhere reachable:
rustemd-tui           # system manager (default socket path)
rustemd-tui --user    # per-user manager
```

The TUI connects over the same unix control socket the CLI uses, so it works
from any terminal with a proper TTY.

## Notes / bugs fixed along the way

Three real issues surfaced while building the e2e test and were fixed in
`rustemd/src/manager/mod.rs`:

1. **Job-engine deadlock on synchronously-failing dependencies.** A unit whose
   start resolves *synchronously* (e.g. `demo.mount` failing `mount(2)` with
   `EPERM`, or a `.target` activating instantly) completed its job inside the
   parent's `expand_start_job` recursion, *before* the parent's `waiting` list
   was committed — leaving a stale wait entry that blocked the parent's start
   job forever (a target would never reach `active`). Fix: drop wait entries
   whose job is no longer pending after expansion.
2. **Re-arming timers blocked clean shutdown.** `idle()` requires
   `!wheel.has_service_timers()`, and a monotonic/calendar timer re-arms itself
   on every state change, so a system with any such timer could never reach
   `idle()` → `run()` never exited → `poweroff` hung. Fix: clear the timer
   wheel on `shutdown()` and stop re-arming timers once `shutting_down`.
3. **Socket activation could re-trigger mid-shutdown.** A pending connection
   left in a `.socket`'s backlog would re-`start()` its service while
   `shutdown()` was stopping it, restarting it faster than it could be stopped
   and blocking poweroff. Fix: `start()` refuses new starts once
   `shutting_down`.

The live env also brings up loopback (`ip link set lo up` in `/init`) so the
TCP `demo.socket` is reachable from the getty shell.

Both are covered by `rustemd/tests/e2e.rs` (see below).

## Automated coverage

`rustemd/tests/e2e.rs` drives the demo units through the programmatic
`Control` CLI client against a real in-process daemon:

- `live_demo_units_lifecycle` — the `examples/live/` set: `.service`,
  `.timer`, `.socket`, `.mount`, `.target` together (`.mount` self-skips when
  not root; run `unshare -m -U -r --map-root-user cargo test --test e2e` to
  exercise it for real).
- `timer_activates_target_on_schedule`, `target_start_pulls_in_wants`,
  `device_units_appear_after_enumeration` — the cheaper per-type assertions.

## Live-env verification (what actually happened)

The live env was booted for real in qemu (KVM, `-nographic`) with commands
piped over the serial console. Observed, from the captured serial log:

- `rustemd manager started` and a getty shell on `/dev/ttyS0` responds.
- `rustemd list-units` shows every demo unit in the right state at boot:
  `demo.mount active(mounted)`, `demo.service active(exited)`,
  `demo.socket active(running)`, `demo.timer active`, `demo.target active`,
  `getty@ttyS0.service active(running)`.
- `udev: 325 devices → 650 .device units` — real `.device` units appear.
- `rustemd status demo.mount` → `Active: active (mounted)`; `/mnt/demo` exists.
- The timer fires: `[demo.timer] triggered demo-tick.service`, then
  `[rustemd demo] tick from demo-tick.service`.
- Socket activation: `nc -z 127.0.0.1 8080` → `demo-echo.service` goes
  `active (running)` (`activated via socket`).
- `rustemd poweroff` → `shutdown complete, powering off` → `reboot: Power
  down`. Clean.
- TUI over serial does **not** render (see the section above).
